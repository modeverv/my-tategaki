# Dockerによる原稿一括出力の実装計画

作成日: 2026-09-27

状態: 初期対象E01〜E04・E06の実装と実機検証を進めた。利用方法は [Docker出力ガイド](docker-export-guide.md)、形式別の検証実績・未対応項目は [検証記録](docker-export-validation.md) を参照。以下は設計時の要件を保持しており、全項目の実装済みを意味しない。E05の印刷所別対応は、具体的な印刷仕様を決めた後の段階とする。

## 1. 目的と現在地

同じ原稿から、出版社へ渡す編集可能なDOCX・TXT、提出／校正用PDF、縦書きEPUBを一括生成する。印刷所へ渡すPDFは、提出先の仕様を持つ追加プロファイルとして実装する。

[既存の機能拡充計画](vertical-editing-implementation-plan.md)のG15を具体化する。[README](../README.md)では、本文編集、青空文庫形式の限定した注記、組版表示、固定版面、アウトライン、脚本モードまで整備されている。一方、画面の固定版面はPDF・EPUBの出力機能ではない。既存文書を根拠にした現状整理であり、この計画作成時には実装全体の監査や既存テストの再実行をしていない。

目標は、Emacsから一度の操作で出力ジョブを開始し、成功したファイルと形式別の検証結果を確認できること。外部依存は出力時だけ必要とし、Docker未導入でも通常の縦書き編集を維持する。

## 2. 対象とする出力

| ID | 出力 | 用途と要件 | 初期対応 |
|---|---|---|---|
| E01 | TXT | UTF-8の原文保存版と本文抽出版。注記の扱い、改行コード、文字コードを明示する | 対応 |
| E02 | DOCX | 編集可能な本文、縦書き、見出し、ルビ、用紙・余白・ページ番号、任意の表紙 | 対応 |
| E03 | 提出／校正用PDF | 縦書き、フォント埋め込み、検索・コピー可能な本文、版面、ルビ、章、ページ番号 | 対応 |
| E04 | リフロー型EPUB 3 | 縦書き、右から左へのページ進行、電子目次、ルビ、縦中横、書誌情報、任意の表紙 | 対応 |
| E05 | 印刷入稿用PDF | 印刷所指定の寸法・色・余白・塗り足し・PDF規格への対応 | 後続段階 |
| E06 | HTMLと検証レポート | 出力プレビュー、変換途中の確認、形式別の成否と警告 | 共通基盤 |

初期の「一括出力」はE01〜E04とレポートを指す。E05は印刷所のプロファイルを指定した場合に追加する。固定レイアウトEPUB、InDesign形式、電子書店へのアップロード、編集済みDOCXの原稿への逆変換は初期対象外。

本文抽出TXTでは、対応するルビの読み・注記を除き、親文字を残す。原文保存版とはファイル名を分ける。未対応・未完成の注記を推測で削除しない。UTF-8以外への変換で表現できない文字はエラーとして原文位置を示し、置換文字で処理を続けない。

## 3. 全体構成と責任分担

```text
Emacsの本文スナップショット／CLIで指定した原稿
  → 共通の注記解析・文書モデル化（Elisp）
  → document.json ＋ source.txt ＋ assets ＋ 出力プロファイル
  → Docker内のPython実行管理
      ├─ TXT出力
      ├─ Pandoc ＋ フィルター ＋ Word参照文書 → DOCX
      ├─ HTML/CSS ＋ Vivliostyle → 提出／校正用PDF
      ├─ HTML/CSS ＋ Vivliostyle → EPUB
      └─ 印刷用設定 ＋ PDF後処理 → 印刷入稿用PDF（任意）
  → 構造・本文・書式の検証
  → ジョブ別出力フォルダー ＋ report.json / report.md
```

| 要素 | 担当 |
|---|---|
| Elisp | 元バッファの取得、既存注記との意味の一致、非同期ジョブ、結果表示 |
| Python | 入力検証、各変換器の実行、タイムアウト、生成物とレポートの管理 |
| Pandoc | DOCXの基本構造・見出し・段落・スタイルの生成 |
| Luaフィルター／必要なOOXML処理 | ルビ、縦中横、傍点等の形式固有の表現。対応可否を試作で決める |
| Vivliostyle | HTML/CSSの組版、PDF・EPUB生成 |
| 検証ツール | EPUBCheck、XML／ZIP検査、PDF情報・文字抽出・ページ描画 |
| Docker | ツール、フォント、依存パッケージの固定と実行環境の分離 |

Pandocだけで全形式の日本語組版を同じように再現できるとは仮定しない。PDF／EPUBはHTML経路を第一候補とし、DOCXには形式固有の調整を置く。Python自身で文字の配置エンジンを作ることは初期範囲に含めない。

## 4. 原稿と中間データの契約

### 4.1 入力の取得

- 既定は現在のバッファ全体。未保存の編集内容もスナップショットに含め、元ファイルの保存は要求しない。
- narrowingや選択範囲を出力する場合は明示指定する。範囲の途中で切れた注記は診断対象にし、親文字や読みを黙って落とさない。
- IME未確定文字、Copilot／Corfuの未採用提案、カーソル、罫線、表示用の約物置換、検索faceは入力に含めない。
- ジョブ開始後の編集は進行中のスナップショットへ反映しない。取得時刻と本文ハッシュを結果に表示する。
- 本文取得・解析でpoint、mark、narrowing、変更フラグ、Undo履歴を変えない。

### 4.2 共通文書モデル

`document.json`にスキーマの版を持たせ、以下を格納する。

- 書誌情報: 題名、著者／筆名、言語、識別子、任意の副題・表紙・奥付。
- 本文構造: 章／見出し、段落、明示改行、空段落、必要な明示改ページ。
- 注記: 親文字と読み、傍点・傍線、明示的な縦中横。
- 元原稿との対応: スナップショット内の開始・終了位置、章ID、段落ID、解析時の警告。
- 原文と意味情報を区別した期待値: 本文、ルビの読み、章の順序、注記の数。

位置はスナップショット先頭を0とするUnicodeコードポイント単位、終了位置は範囲外と定義する。Emacsのバッファ位置、UTF-8のバイト位置、表示セルの位置を混同しない。原文へのUnicode正規化・自動誤字修正は行わない。

既存の注記解析を再利用できる境界を調べ、画面配置・SVG・ウィンドウ状態に依存しない取り出し口を用意する。Python側へ別の青空文庫パーサーを増やさない。CLI入力にも同じElispの解析を使い、必要な場合はDocker内のバッチEmacsで実行する。ユーザーのinit.elやGUIを読み込まない。

初期入力はプレーンテキストと現在対応する青空文庫注記を基準にする。Org／Markdownの全文を自動で再解釈しない。見出しを構造として扱うか、記号込みの本文として残すかを入力設定に持たせ、章名・順序の期待値を変換前に確定する。数式・生HTMLなどの暗黙の解釈による本文や章の欠落を防ぐ。

未対応記法は原文と警告を保持する。試読用は警告付き出力を許容し、提出用の厳格設定では未解決の注記エラーがある形式を成功扱いにしない。

### 4.3 形式別の保持範囲

| 情報 | TXT | DOCX | PDF | EPUB |
|---|---|---|---|---|
| 本文・段落・空行 | 保持 | 編集可能な文字として保持 | 文字として保持 | XHTMLの文字として保持 |
| 章 | 記号を残す／設定に従い抽出 | 見出しスタイル | 見出し・しおり | 見出し・電子目次 |
| ルビ | 記法を残す／読みを除く | Wordのルビを目標に試作 | HTML rubyを組版 | HTML ruby |
| 傍点・傍線・縦中横 | 記法を残す／除く | 対応するOOXMLを試作 | CSS／HTMLで組版 | 対応CSSと実閲覧確認 |
| 自動縦中横 | 本文は変更しない | プロファイル設定に従う | 同左 | 同左 |
| 固定字数・列数 | 書式情報を持たない | 原稿用紙設定を試作 | 固定版面として検証 | 固定しない |

代替表現を使った場合はレポートに記録する。ルビを単なる括弧書きへ変えるなどの意味変更は、指定なしに行わない。

## 5. 形式別の設計

### E02: Word原稿

- Pandocの参照DOCXに見出し・本文・用紙・余白・ヘッダー／フッターを用意する。
- 縦書き方向、文書グリッド、ルビ、傍点、縦中横のうち参照文書で維持されない項目を試作で特定し、Luaフィルターまたは生成後のOOXML処理に分ける。
- 段落を通常のWord段落として出力する。行末を合わせるために文字ごとに表やテキストボックスへ分割しない。
- 指定字数×行数の再現性を、実際のWordと採用する日本語フォントで確認する。LibreOfficeの表示だけでWordでの確認完了とはしない。
- 修正・コメントを行える本文を目標とする。変更履歴の生成やDOCXからの差分取り込みは後続機能に分ける。

### E03: 提出／校正用PDF

- HTMLの段落・見出し・rubyと、印刷専用CSSからVivliostyleで生成する。
- 用紙、余白、縦書き、文字サイズ、行間、章の開始、柱、ページ番号、任意の表紙を設定する。
- 固定字数・列数はフォントと版面を合わせたプロファイルとして検証する。禁則・ぶら下げ・ルビがある場合の「指定字数」の意味も文書化する。
- 本文を検索・コピー可能にし、使用フォントと欠落字形を検査する。
- 画面とPDFでは組版エンジンが異なるため、同じ改ページを初期保証に含めない。正式な出力結果は生成PDFで確認する。
- DOCXとPDFのページ番号が完全一致することも初期保証に含めない。Word原稿と厳密に同じPDFが必要な用途は、同じWord環境からの書き出しを別経路として検討する。

### E04: EPUB

- リフロー型EPUB 3を生成する。本文の縦書きと、右から左へのページ進行をそれぞれ明示する。
- 共通HTMLの章・注記を使い、EPUB向けCSSを分ける。印刷専用の用紙寸法、柱、ページ番号を本文へ混入させない。
- 電子目次、章ID、書誌情報、任意の表紙を構成する。初期範囲外の画像・脚注等が入力に現れた場合の扱いは診断する。
- 読者による文字サイズ変更を保ち、端末ごとに改ページが変わることを仕様とする。
- Vivliostyleの日本語EPUB向けテーマを候補にし、互換性を実読書アプリで確認する。PandocのEPUB writerへの切り替えは、同じ検証原稿で必要性が確認された場合の代替案とする。

### E05: 印刷入稿用PDF

- 提出用PDFとは設定とファイル名を分ける。
- 印刷所の仕様に応じ、仕上がり寸法、綴じ側の余白、単ページ／見開き、色、塗り足し、トンボ、PDF規格を設定する。塗り足し・トンボを全出力へ一律に付けない。
- VivliostyleのPDF/X-1a生成・press-ready連携を第一候補として検証する。PDF/X-4等を要求する提出先には、検証した別経路ができるまで未対応と表示する。
- Docker内からホストのDockerソケットへ接続する構成は採らず、必要な後処理ツールを同じ実行イメージ内で使う方式を試す。
- 本文PDFと表紙PDFを別成果物にする。表紙の背幅・製本条件は印刷所の仕様が決まってから扱う。
- 変換成功と入稿条件の合格を区別し、未検証の条件を「入稿可能」と表示しない。

## 6. Docker環境とフォント

- Docker Composeの一回実行サービスを使う。ホスト側の必要物はDockerと起動用スクリプトとし、Python・Pandoc・Node.js・Java等をホストに要求しない。
- 実行イメージにPython、Pandoc、Vivliostyle CLI／対応ブラウザ、Java／EPUBCheck、PDF情報・文字抽出・描画ツール、日本語フォントを入れる。CLIでの原稿解析用にバッチEmacsを含める設計を試作する。
- ベースイメージ、ツール、Python／Node依存、ブラウザ、フォントを固定する。具体的な版は段階0で動作確認して決定し、計画時点の推測で固定しない。
- 初期の動作確認対象はApple Silicon上のDockerとする。linux/amd64も別に確認し、未確認のアーキテクチャを対応済みと記載しない。
- 入力スナップショット・素材は読み取り専用で渡し、書き込み先はジョブ専用の作業／出力ディレクトリにする。日本語・空白を含むパス、ファイル所有権を確認する。
- 初回のイメージ取得・構築と、通常の原稿変換を区別する。通常実行では必要な素材をローカルに揃え、ネットワークなしで完結する構成を目標にする。
- 標準の明朝・ゴシックを同梱し、出力・埋め込みが可能なライセンスのものを選ぶ。ユーザーフォントは明示的な追加指定にする。
- フォントのファイルとハッシュ、実際に使った代替フォントを記録する。必須フォントがない場合に無通知で置き換えない。
- 再現性はまず本文構造と版面を基準にする。PDF等の時刻情報による差もあるため、ファイル全体のバイト一致は別の課題として扱う。

## 7. 出力プロファイルと操作

### プロファイル

共通書誌情報と形式別設定を分離する。設定ファイルはYAML等を想定し、スキーマ検証して使用する。

| 設定群 | 内容 |
|---|---|
| 入力 | 原文／見出し解釈、注記の厳格さ、全体／明示範囲 |
| 書誌情報 | 題名、筆名、言語、表紙、必要な奥付 |
| 提出原稿 | 用紙、縦横、字数・行数、余白、ページ番号、表紙・あらすじ |
| 印刷 | 製本方向、仕上がり、色、塗り足し、PDF規格 |
| EPUB | 目次の深さ、縦書き設定、CSS、表紙、識別子 |
| 検証 | 必須項目、警告の扱い、確認対象アプリ |

初期プリセットは一般的な試読用と、字数・行数を明示できる投稿用にする。出版社・賞の名前を付ける設定には参照URLと確認日を持たせる。特定年度の応募条件を固定の普遍的ルールにしない。

文字数÷400の換算、20字×20行で配置した枚数、実際の出力ページ数を区別する。どの値を表紙に記載するかを設定に持たせ、Emacsの画面ページ数を提出枚数に流用しない。

連絡先などの応募用情報は提出用の別紙／表紙に限定し、EPUBの公開メタデータへ自動転用しない。

### コマンド案（未実装）

```sh
./bin/tategaki-export export manuscript.txt \
  --profile submission \
  --formats txt,docx,pdf,epub \
  --out ./dist
```

- `tategaki-export`: 形式・プロファイルを選んで出力。
- `tategaki-export-all`: 初期対応の全形式を一括出力。
- `tategaki-export-status`: 進行状況・結果を表示。
- `tategaki-export-cancel`: 自分が開始したジョブだけを停止。

Elispは引数リストを使って非同期プロセスを起動し、シェル文字列へ原稿名等を埋め込まない。通常の編集を止めず、別バッファに段階・ログ・結果を表示する。

出力は `dist/<job-id>/` にまとめる。既存の成果物を上書きせず、ジョブIDには入力・設定のハッシュと衝突しない識別子を使う。レポートには入力ハッシュ、設定、ツール／フォントの版、処理時間、形式別の成功・失敗・警告・未確認事項を含める。

共通入力の検証失敗はジョブ全体を止める。形式ごとの生成失敗では他の独立した形式を続行し、全体の終了状態は失敗を返す。未指定の形式と、指定したが作れなかった形式を区別する。一時ファイルは成功した成果物へ昇格させるまで完成品として扱わない。

## 9. 実装順序と完了条件

| 段階 | 作業 | 完了条件 |
|---|---|---|
| 0: 調査・試作 | 既存解析の取り出し口を確認。代表原稿からDOCX・PDF・EPUBを生成。ツール・フォントを選ぶ | 3形式の本文・章・ルビ・縦中横を実表示で確認。未対応項目と代替案を記録 |
| 1: 共通基盤 | Docker、起動スクリプト、文書モデル、入力スナップショット、TXT、レポート | ホストのPython等に依存せず実行でき、元原稿不変・入力ハッシュ・失敗状態を確認 |
| 2: 提出原稿 | Pandoc経路、Wordテンプレート、注記、Vivliostyleの提出用PDF | 同じ原稿から編集可能なDOCXと読める縦書きPDFを出し、文字・注記・書式を検証 |
| 3: EPUB | 目次・書誌情報・表紙・専用CSS・EPUBCheck | 構造検証に合格し、対象アプリで縦書き・注記・文字サイズ変更を確認 |
| 4: 一括操作 | 全形式の実行、Emacs連携、進捗、取消、部分失敗、再実行 | 編集を止めず一括出力でき、各形式の結果と未確認項目を利用者が確認できる |
| 5: 印刷対応 | 印刷所別のPDFプロファイル、PDF後処理、プリフライト | 合意した一つの印刷仕様について生成物を検査し、対応範囲を限定して記録 |
| 6: 回帰・文書化 | 長文、文字の境界例、既存編集、環境差、利用手順 | 失敗・スキップを含む実績を記録し、READMEに対応形式・条件・操作を反映 |

最初の実装単位は「代表原稿1本をDocker内でDOCX・PDF・EPUBに変換する試作」とする。Wordの縦書き・注記が成立するかを早期に確かめ、成立前に一括UIや大量の提出先テンプレートを作り込まない。

## 10. 検証計画

### 代表原稿

短い共通原稿に、複数章、空段落、会話、明示改行、長いルビ、漢字に続くルビ、傍点・傍線、明示／自動の縦中横、英語、URL、結合濁点、異体字、絵文字、未完成・未対応の注記、記号を含む見出しを含める。脚本形式も別の短い原稿で扱う。章・段落・親文字・読みの期待値は、変換処理と独立に固定する。

長文は1万・10万・20万字で、短段落多数と長い単一段落、注記が多い場合を用意する。処理時間・最大メモリ・初回と再実行の違いを記録する。達成時間の数値は試作前に保証しない。

### 自動検証と実表示

| 対象 | 確認内容 |
|---|---|
| 文書モデル | 原文範囲、章の数と順序、本文・読みの保持、未対応記法、範囲選択の境界 |
| TXT | 原文保存版の文字列一致、本文抽出版の親文字、文字コードエラー |
| DOCX | ZIP／XML、見出し・段落・ルビの構造、本文／読みの分離照合、設定の保持 |
| Word実表示 | 縦書き、指定字数・行数、ルビ・縦中横、再編集、改ページ。確認したWordの版とフォントを記録 |
| PDF | ページ寸法、埋め込みフォント、欠落字形、本文抽出、全ページの描画、列末・改ページの欠落や衝突 |
| EPUB | EPUBCheck、ZIP／XML、mimetype、目次／spineと原稿の章順、メタデータ、リンク、本文・注記 |
| EPUB実表示 | Apple BooksとKindle Previewerを初期候補にし、縦書き・ページ進行・ルビ・目次・文字サイズ変更を確認 |
| ジョブ | Docker未起動、タイムアウト、取消、同時実行、出力不可、部分失敗、日本語・空白を含むパス |
| Emacs | 未保存本文、narrowing、範囲出力、IME／補完の除外、point・Undo・元ファイル不変、ジョブ中の編集 |

変換器の終了コードだけで本文保持を判断しない。変換前後で章の数・順序・本文を照合し、途中の章が欠落するケースを検出する。DOCXやEPUBは親文字とルビの読みを構造として分けて比較する。

PDFの抽出順序は縦書き・ルビにより変わることがあるため、単純な全文一致だけを合否基準にしない。抽出規則と許容する差を限定し、元の文書モデルとの照合と実ページの確認を併用する。広い空白除去や文字の並べ替えで欠落を隠さない。

EPUBCheckの成功は閲覧アプリでの表示保証ではない。PDF/Xへの変換成功も、任意の印刷所への適合保証ではない。それぞれの実表示・入稿仕様の確認結果を分けて記録する。

### リリース条件

- [ ] 初期対象の全形式を、同じスナップショットから一括生成できる。
- [ ] 原稿と生成物で、本文・章・対応注記の欠落や意図しない変換がない。
- [ ] Wordと対象EPUBアプリでの確認結果があり、未確認環境を明示している。
- [ ] PDFの全ページを描画し、代表原稿のページ境界・ルビ・縦中横を確認している。
- [ ] 元バッファ・保存ファイル・Undoを変えず、出力中も編集できる。
- [ ] 実行環境、フォント、入力・設定ハッシュ、検証結果を再現可能な形で残す。
- [ ] Dockerなしでも既存の編集が使え、出力の依存不足を明確に案内する。
- [ ] 既存の編集機能に関係する変更には適切な回帰確認を実施し、実行範囲を記録する。

## 11. 試作で解決する論点

1. 既存の注記解析を、GUIや画面キャッシュから独立して呼べるか。
2. Wordの縦書き、原稿用紙グリッド、ルビ・傍点・縦中横を、どこまでテンプレートとフィルターで保持できるか。
3. PDFで必要な固定字数・行数と禁則・ルビの配置を、採用フォントで再現できるか。
4. VivliostyleのEPUB経路で、対象アプリの表示と電子目次が十分に成立するか。
5. Apple Silicon上でブラウザを含むコンテナが動作し、初回構築時間・イメージ容量・長文性能が実用範囲に収まるか。
6. 印刷用の後処理を同一コンテナ内で完結できるか。対応できるPDF規格はどれか。
